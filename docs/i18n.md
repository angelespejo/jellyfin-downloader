# Internationalization

The app is translated into English, Spanish and Catalan with a small native
i18n layer and no runtime dependency.

## Files

- `src/locales/en.ts` — source of truth and `MessageKey` type;
- `src/locales/es.ts` — Spanish dictionary;
- `src/locales/ca.ts` — Catalan dictionary;
- `src/lib/i18n/translate.ts` — resolution, interpolation and error lookup;
- `src/core/i18n.svelte.ts` — reactive context and cookie persistence.

Adding a key requires updating all three dictionaries; TypeScript enforces
parity.

## Detection

1. Cookie `jd_locale_mode`: `auto`, `en`, `es` or `ca`.
2. If `auto`, the first `Accept-Language` tag on the server, or the first
   `navigator.language` on the client.
3. `es*` → Spanish, `ca*` → Catalan, any other language → English.
4. No header → English.

The URL is not rewritten. The selected value is stored in a cookie so SSR is
consistent after reloads.

## SSR

`hooks.server.ts` sets `event.locals.locale` and replaces `%lang%` in
`app.html`. `+layout.server.ts` exposes it; `+layout.svelte` creates the i18n
context. The client updates `document.documentElement.lang` on change.

## Errors

Server/API messages are English. The UI calls `i18n.error(code, fallback)` and
maps stable codes such as `COPY_CANNOT_SCALE` or `BURN_UNSUPPORTED` to localized
messages.

## Formatting

Dates, languages and numbers use `Intl` with the active locale. Components must
pass `i18n.locale` to `formatTimestamp`, `formatLanguage` and `formatBytes`.

## Rules

- Never hardcode user-visible text in components.
- Keep `en`, `es` and `ca` keys in sync.
- Use `{name}` placeholders for interpolation.
- Test detection behavior in `tests/unit/i18n.test.ts`.
